## 0. 摘要

功能主干是可靠的：OCR 识别、五种导出、PDF 逐页、表格网格、长截图拼接、剪贴板、翻译主备链路在本轮全部实测通过，没有发现数据错误类缺陷（上一轮修掉的表格「姓 名」空格问题已复测确认不复现）。

问题集中在**持久化状态的健壮性**和**长任务对主线程的占用**上：

| 级别 | 数量 | 性质 |
| --- | --- | --- |
| P0 阻断 | 3 | 程序起不来 / 用户数据被静默吞掉 |
| P1 高 | 6 | 功能静默失效、界面冻结、内存占用失控 |
| P2 中 | 5 | 特定条件下报错或体验退化 |
| P3 低 | 4 | 防御性不足，当前调用路径不可达 |

**最需要立刻处理的一条**：`history.json` 或 `settings.json` 只要有一处结构不合法，程序会在构造窗口时抛出异常，**表现为双击后没有任何窗口**，普通用户无法自行恢复，也不知道该删哪个文件。这两个文件都在 `%APPDATA%\SnapOCR\` 下，且没有损坏时的自愈逻辑。

## 2. 缺陷清单

> 严重度定义：**P0** 程序无法使用或数据丢失；**P1** 功能静默失效、明显卡死、资源失控；**P2** 特定条件下报错；**P3** 防御性缺陷，当前路径不可达。

### P0-1　`history.json` 结构异常导致程序无法启动

**现象**：`history.json` 内容只要是合法 JSON 但元素结构不对，`MainWindow` 构造即抛异常，双击程序没有任何窗口出现（控制台版会看到 traceback，GUI 版静默退出）。

**复现步骤**
1. 打开 `%APPDATA%\SnapOCR\history.json`
2. 改成 `[1, 2, 3]`（或 `["abc"]`、`[{"time":"t"}]`、`[{"time":"t","text":null}]`、`[null]`）
3. 启动 SnapOCR

**预期**：跳过无法解析的记录，正常启动，最好提示一次「历史记录有损坏，已跳过 N 条」
**实际**：`TypeError: 'int' object is not subscriptable` / `KeyError: 'text'` / `AttributeError: 'NoneType' object has no attribute 'replace'`，程序不启动

**实测**：11 个用例中 8 个崩溃（详见附录 A）

**根因**
- `app/ui/main_window.py:904` `_load_history()` 只判断了 `isinstance(data, list)`，没有校验元素结构
- `app/ui/main_window.py:929-935` `_refresh_list()` 直接 `item["text"].lower()`、`item["text"].replace(...)`、`item["time"]`

**触发场景**（都是真实可能）：写入过程中断电导致文件截断、用户手工编辑、其他工具改写、从旧版本迁移

**修复建议**
```python
def _load_history(self) -> list[dict]:
    try:
        with open(config.HISTORY_FILE, encoding="utf-8") as f:
            data = json.load(f)
    except Exception:
        return []
    if not isinstance(data, list):
        return []
    clean = []
    for it in data:
        if not isinstance(it, dict):
            continue
        text = it.get("text")
        if not isinstance(text, str) or not text:
            continue
        ts = it.get("time")
        clean.append({
            "time": ts if isinstance(ts, str) else "未知时间",
            "text": text,
        })
    return clean
```
同时建议 `_refresh_list` 里对 `item.get("text")` 再做一次类型兜底（防御第二道）。

**验证方式**：附录 A 脚本，11 个用例必须全部 `[OK]` 且列表条目数正确。

### P0-2　`settings.json` 热键值类型错误导致程序无法启动

**现象**：`settings.json` 里 `hotkey_capture` 是 `null` / 数字 / 数组时，启动崩溃。

**复现步骤**
1. 把 `%APPDATA%\SnapOCR\settings.json` 改成 `{"hotkey_capture": null}`
2. 启动 SnapOCR

**预期**：回退到默认热键 `ctrl+alt+q` 并正常启动
**实际**：`AttributeError: 'NoneType' object has no attribute 'upper'`，程序不启动

**实测**：9 个用例中 3 个崩溃（`null` / `123` / `["a"]`）；空字符串、非法语言码、布尔写成字符串、顶层是列表、JSON 语法错误都能正常启动

- `app/ui/main_window.py:807` `_tip_html()` 里 `config.HOTKEY.upper()` 是启动必经路径（`_build_ui` → `_build_capture_page` → `QLabel(self._tip_html())`）

```python
def _hotkey_or(value, default: str) -> str:

HOTKEY = _hotkey_or(_settings.get("hotkey_capture"), HOTKEY)
TRANSLATE_HOTKEY = _hotkey_or(_settings.get("hotkey_translate"), TRANSLATE_HOTKEY)
HOTKEY_LONG = _hotkey_or(_settings.get("hotkey_long"), HOTKEY_LONG)
```

**验证方式**：附录 B 脚本，9 个用例全部 `[OK]`，非法值回退到默认热键。

### P0-3　多实例并存：历史记录互相覆盖丢失

**现象**：同时运行两个 SnapOCR（双击两次、或从两个快捷方式启动），两个窗口各自识别的内容会互相覆盖，**后写入的实例会抹掉先写入实例本次新增的全部记录**。

**复现步骤**
1. 启动实例 A、实例 B（`history.json` 初始为空）
2. 在 A 里识别一段文字 → 保存
3. 在 B 里识别另一段文字 → 保存
4. 查看 `history.json`

**预期**：两条记录都在
**实际**：只剩 B 的那条，A 的记录在磁盘上永久消失（A 内存里还有，但下次 A 再识别会反过来覆盖 B）

**实测**：磁盘最终 1 条 `['B 实例识别的内容']`（附录 C）

**根因**
- 没有单实例保护：全项目搜不到 `QLocalServer` / `QSharedMemory` / `QLockFile`
- `_add_history` 是「内存列表全量重写」模型（`main_window.py:912-923`），两个进程各自持有一份快照

**附带影响**：两个实例都会注册全局热键，Windows 下每个进程各自安装低级键盘钩子，**按一次 `ctrl+alt+q` 会弹出两个截图遮罩**。

**修复建议**
1. 首选：加单实例锁，第二次启动时激活已有窗口后退出
```python
# app/main.py
from PySide6.QtNetwork import QLocalServer, QLocalSocket
sock = QLocalSocket()
sock.connectToServer("SnapOCR-single")
if sock.waitForConnected(200):
    sock.write(b"show"); sock.flush()   # 让已有实例 showNormal()
    sys.exit(0)
QLocalServer.removeServer("SnapOCR-single")
server = QLocalServer()
server.listen("SnapOCR-single")
```
2. 次选（不改架构）：`_add_history` 写盘前重新读一次磁盘，按 `(time, text)` 去重合并

**验证方式**：附录 C 脚本，两个实例各写一条后磁盘应有 2 条；单实例锁生效时第二个进程应立即退出。

### P1-1　历史写入失败无兜底，且非原子写

**现象**：`history.json` 只读、目录被占用、磁盘满时，`_add_history` 抛 `PermissionError` 且**内存已插入、磁盘没写入**，界面看起来正常但记录丢了。

**复现步骤**
1. `history.json` 设为只读（或把同名目录建在文件位置）
2. 识别一段文字

**预期**：提示「历史保存失败」，或至少降级为内存保留
**实际**：异常在 Qt 槽里冒泡（`Traceback` 打到 stderr，用户看不到）；内存 1 条 / 列表 0 条，两边不一致

**实测**：附录 D，A/B 两段均 `PermissionError`，`内存历史条数: 1` 而 `列表条目: 0`

**根因**：`main_window.py:912` `_save_history` 无 `try`，直接 `open(..., "w")` 覆盖写 —— 中途失败会把原文件截断成半截 JSON，进而触发 P0-1

**修复建议**：原子写 + 失败提示
```python
def _save_history(self) -> None:
    try:
        os.makedirs(config.DATA_DIR, exist_ok=True)
        tmp = config.HISTORY_FILE + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump(self._history, f, ensure_ascii=False, indent=1)
        os.replace(tmp, config.HISTORY_FILE)   # 同分区原子替换
    except OSError as exc:
        self.statusBar().showMessage(f"历史保存失败：{exc}", 8000)
```

**验证方式**：只读场景下应出现 statusBar 提示且原有文件内容不被破坏（长度不变）。

### P1-2　批量识别把全部图片读进内存，且在主线程读取

**现象**：点「开始识别」时，所有图片被一次性 `open().read()` 到内存，**读取发生在 GUI 线程**，图片多时会先卡一下，之后全程常驻等量内存。

**复现步骤**
1. 批量队列放入 500 张 1080p 截图
2. 点「开始识别」

**实测**（附录 E）

| 队列 | 磁盘 | 读取耗时（GUI 线程） | 常驻内存 |
| --- | --- | --- | --- |
| 500 张 1080p | 616 MB | **1.08 s** | **616 MB** |
| 12 张 4K | 59 MB | 0.05 s | 59 MB |

500 张手机照片（每张 3 MB）就是 1.5 GB，32 位或内存紧张机器会直接 OOM 崩溃。

**根因**：`main_window.py:1111-1116` 在 `_on_batch_start` 里同步读全部文件，构造 `list[tuple[str, bytes]]` 后交给 worker

**修复建议**：worker 只收路径，自己逐张读
```python
class OcrWorker(QThread):
    def __init__(self, image=None, paths: list[str] | None = None): ...
    def run(self):
        for p in self._paths:
            try:
                with open(p, "rb") as f:
                    data = f.read()
            except OSError as exc:
                parts.append(f"== {os.path.basename(p)} ==\n[读取失败] {exc}")
                continue
            ...
```
这样内存峰值从「全部图片之和」降到「单张 + 结果文本」。

**验证方式**：500 张用例下，主线程耗时应 < 0.1 s，常驻内存增量应接近 0。

### P1-5　热键重注册失败后不回滚、不提示（静默失效）

**现象**：在设置里改成无效组合并保存，界面显示「设置已保存」，但全局热键实际已失效，用户按了没反应，也不知道原因。

**复现步骤**
1. 设置 → 快捷键，录一个非法组合
2. 点确定

**预期**：提示「该快捷键无法注册」，并保留原设置
**实际**：`config.HOTKEY` 被改成无效值（未回滚），状态栏为空，随后被 `_open_settings` 末尾的「设置已保存」覆盖

**实测**（附录 B 末段）：`config.HOTKEY = 'a-bad-key'`（未回滚）、`_hotkey_error` 有值但**状态栏为空**

**根因**
- `main_window.py:887-901` `_reregister_hotkeys_safely` 的 `try/except` 永远不触发 —— 因为 `_register_hotkey` 内部已把异常吞掉并只设置 `_hotkey_error`，自己不会抛
- 失败提示只在 `_deferred_start` 里 `showMessage`，重注册路径没有

**修复建议**
```python
def _register_hotkey(self) -> bool:
    ...
    if not (ok1 and ok2 and ok3):
        self._hotkey_error = "热键注册失败：可能与其他程序冲突，请换一个组合"
        return False
    self._hotkey_error = ""
    return True

def _reregister_hotkeys_safely(self) -> None:
    old = (config.HOTKEY, config.TRANSLATE_HOTKEY, config.HOTKEY_LONG)
    keyboard.unhook_all()
    if self._register_hotkey():
        return
    keyboard.unhook_all()
    config.HOTKEY, config.TRANSLATE_HOTKEY, config.HOTKEY_LONG = old
    self._register_hotkey()
    QMessageBox.warning(self, config.APP_NAME,
        f"快捷键注册失败，已恢复原设置。\n{getattr(self, '_hotkey_error', '')}")
```
另外把提示文案里的「Linux 需 root，macOS 需辅助功能权限」改成按平台分支 —— 在 Windows 上出现这句会误导用户排查方向。

**验证方式**：mock `keyboard.add_hotkey` 抛异常，断言 `config.HOTKEY` 等于原值且弹出了警告。

### P1-6　单键热键可被接受，会劫持全局按键

**现象**：设置里录一个单键（如 `A`）或纯修饰键（`Ctrl+Shift`），能被保存并注册成功。之后**每次按 A 都会触发截图**，全系统打字都会被干扰。

- `settings_dialog.py:29-38` `_seq_to_hotkey` 不做修饰键检查

**修复建议**
```python
_MODS = ("ctrl", "alt", "shift", "windows")

def _valid_hotkey(hk: str) -> bool:

    has_mod = any(p in _MODS for p in parts)
    has_key = any(p not in _MODS for p in parts)
```

### P2-1　`_upscale_small` 对 0 尺寸输入除零

**复现**：`_upscale_small(np.zeros((0, 0, 3), np.uint8))` → `ZeroDivisionError`

**实测**：`0x0` 与 `0 宽` 均崩溃；`1x1` 正常放大到 `3x3`

**可达性**：低。截图路径有 `width() < 8` 保护，PDF 渲染失败会走「渲染失败」分支。但 `recognize_array` 是公开入口，被 `recognize_image`、`recognize_table`、`pdf_ocr` 三处调用，任一上游传入空图即崩。

**修复**
```python
h, w = arr.shape[:2]
min_side = min(h, w)
if min_side <= 0:
    return arr
```

**验证方式**：`0x0`、`0 宽` 应原样返回不抛异常。

### P2-2　超长单行文本翻译只切一次，仍会发出超限请求

**现象**：`translate_text` 对超过 5000 字符的**单行**文本只切成两段（5000 + 剩余），剩余部分不再继续切。

**实测**（附录 I）：25000 字符单行 → 请求 2 次，长度 `[5000, 20000]`，第二段仍是阈值的 4 倍。必应接口对超长文本通常拒绝，之后回退 MyMemory（480 字节一片，中文约 160 字），100 万字符会产生 6000+ 次请求 × 0.2 s 限速 ≈ 20 分钟。

**修复**：把「切一段」改成循环切
```python
def _chunk_chars(text: str, limit: int) -> list[str]:
    return [text[i:i + limit] for i in range(0, len(text), limit)]

for para in text.splitlines(keepends=True):
    if len(para) > _MAX_CHARS:
        parts.extend(_chunk_chars(para, _MAX_CHARS))
    ...
```
顺带建议：长文本翻译给个进度提示（现在只有「翻译中...」，几十秒不动用户会以为卡死）。

**验证方式**：25000 字符单行 → 每段 ≤ 5000。

### P2-3　预热线程异常未捕获，失败后静默

**现象**：`EnginePreloader.run` 只调 `get_engine().warmup()`，没有 `try`。模型加载/下载失败时 traceback 打到 stderr，线程直接结束，界面无任何提示。

**实测**：mock 让 `warmup` 抛异常，输出 `Error calling Python override of QThread::run(): ... RuntimeError`

**影响**：用户不知道预热失败，首次截图仍要等模型加载；如果失败原因是磁盘/网络，首次识别也会失败。

**修复**：`try/except` + `statusBar` 提示（需要给 `EnginePreloader` 加 `fail` 信号，连到主窗口）

---

### P2-4　长截图取消时可能丢弃仍在运行的 QThread

**现象**：`_on_longshot_cancel` 里 `w.stop()` 后 `wait(3000)`，超时就把 `self._longshot_worker = None`。若线程仍在 `mss.grab` 里（截大区域或系统卡顿），Python 引用被回收时 Qt 会报 `QThread: Destroyed while thread is still running`，严重时进程崩溃。

**可达性**：需要 grab 卡住超过 3 秒，概率不高。**未做动态验证**——长截图会移动真实鼠标，本轮不干扰桌面。

**修复**
```python
if w.isRunning():
    w.stop()
    if not w.wait(5000):
        w.finished.connect(w.deleteLater)   # 保留引用，交给 Qt 回收
        return
```

### P2-5　截图遮罩只覆盖主屏

**现象**：`capture_overlay` 用 `grab_primary_screen()` + `primaryScreen().geometry()`，副屏既不在遮罩内也无法框选。多屏用户只能截主屏。

**实测**：本机单屏，无法验证多屏行为；代码是单屏路径（`capture_overlay.py:10-16, 37`）

**修复**：按 `QGuiApplication.screens()` 计算虚拟桌面矩形，用 `mss.monitors[0]` 抓整个虚拟桌面，遮罩 `setGeometry` 到虚拟桌面。

- **触发**：批量识别 500 张、首次下载模型（预热）、PDF 逐页识别、翻译请求进行中，
  点「退出」。`_quit()` 对 `_pdf_worker / _table_worker / _batch_worker / _preload`
  只做 `wait(10000)` 且**不检查返回值**，超时后照样 `QApplication.quit()`；
  `TranslateWorker` 则完全没被等待。
- **影响**：进程被 Qt 判为 `QThread: Destroyed while thread is still running` 直接 abort
  （实测退出码 **127**，对照组 `wait()` 后退出为 0）。表现为「退出时闪退/无响应」，
  任务栏残留进程。
- **根因**：`wait()` 结果被忽略；且 `OcrWorker` 没有取消入口，500 张队列根本等不完。
- **修复**：`_quit()` 改为「先请求取消（`OcrWorker` 新增 `cancel()`，逐张检查）→
  所有线程共享 3 秒收尾预算 → 仍在跑的登记进 `_quit_waiting`，全部 `finished` 后再
  `QApplication.quit()`」；翻译线程通过 `TranslateDialog.active_worker()` 纳入同一套等待。
- **验证**：翻译线程运行中退出 → 等待 2.7 s 后正常退出，退出码 0（修复前 127）；
  批量识别 5 张（每张 2 s）中退出 → `_quit` 阻塞 2.0 s，取消生效，退出码 0。

#### P1-2　遮罩/控制条被非 Esc 方式关闭后，截图功能永久失效

- **触发**：框选时按 `Alt+F4`（或任何 WM 关闭），遮罩走 `close()` 而不是 Esc 分支。
- **影响**：`cancelled` 从不发出，主窗口 `self._overlay` 仍指向**已销毁的 C++ 对象**。
  此后 `start_capture()` 里 `if self._overlay is not None: return` 永远成立 ——
  截图/翻译/长截图/表格/贴图**全部无响应，只能重启程序**。
  长截图控制条同理：`_longshot_bar` 悬挂后，截图被永久拦住并提示「长截图会话进行中」，
  后续 `_close_longshot_bar()` 还会在 Qt 槽里抛 `RuntimeError`。
- **修复**：两个控件都加「已结束」标志与 `closeEvent`：
  - `CaptureOverlay.closeEvent` 未结束则补发 `cancelled`；`_finish`/Esc 先置位避免重发。
  - `LongShotBar.closeEvent` 未主动关闭则补发 `cancelClicked`；新增 `dismiss()` 供正常结束使用。
  - 主窗口新增 `_overlay_alive() / _longshot_alive()`：访问时捕获 `RuntimeError` 并清理引用。
- **验证**：`ov.close()` 后 `_overlay` 变 `None`，再调 `start_capture()` 能正常弹新遮罩；
  控制条异常关闭后截图不受阻。

#### P1-3　表格识别：行内空单元格让右侧列整体左移（导出 Excel 错列）

- **触发**：表格某行中间一格为空（合并单元格、缺值、留白），其余行是三列。
- **影响**：旧算法用「行内间隙中点」当列边界。空单元格造成的**大间隙会在中间凭空
  多切一列**，同时填充时用 `sorted(cells.items())` 把单元格**左顶**，结果
  `['苹果','3.5','','']` —— 第 3 列的数字跑到第 2 列，导出 Excel 后整列错位，
  且没有任何报错（静默数据错误）。
- **修复**：重写为「行内切单元格 → 全局列带区间合并 → 单元格按列带落位」：
  `_cells_from_row` / `_column_bands` / `_best_column`，每行长度恒等于列数，
  空格留 `""`；只有真正重叠/相邻的区段才合并为同一列。
- **验证**：真实渲染的 3×3 表格图（中间格故意留空）识别结果为
  `[['姓名','数量','价格'], ['苹果','','3.5'], ['香蕉','7','2.0']]`，
  3 行 3 列、数字仍在第 3 列（修复前为 4 列且错位）。

### 7.3 P2 级（特定环境失效 / 资源风险）

#### P2-1　HiDPI 下长截图控制条跑到别处（本机 125% 必现）

- **触发**：Windows 缩放 125%/150%，框选后点长截图。
- **影响**：`regionSelected` 给的是 **mss 物理像素**，`LongShotBar.move()` 用的是
  **Qt 逻辑坐标**。本机 1536×864 逻辑屏 / 1920×1080 物理屏，选区在 (100,120) 时
  控制条按物理值算到 y≈780，被夹到屏幕底部 —— 离选区几百像素，用户找不到「开始」。
- **修复**：`regionSelected` 增加第 5 个参数（逻辑 `QRect`），控制条用它摆位；
  物理坐标继续只给 `StitchWorker`（mss 需要）。顺带用 `screenAt(选区中心)` 支持副屏。
- **验证**：物理 (236,284,728,488) + 逻辑 (100,120) → 控制条落在 (100,328)，
  正好在选区下方 8px。

#### P2-2　设置里「截图贴图」开关是空转的

- **触发**：设置 → 功能 → 取消勾选「截图贴图」，仍点「截图贴图」。
- **影响**：`config.OCR_PIN` 只被写入和读回，**全代码没有任何地方读它**，功能照常触发。
  同类对比：`OCR_TABLE` / `OCR_PDF` 都有入口检查。
- **修复**：`start_capture(pin=True)` 先检查 `config.OCR_PIN`，关闭时提示去设置里开启。
- **验证**：关闭后调用不再创建遮罩，且弹出提示。

#### P2-3　超大尺寸 PDF 页面单页吃掉 306 MB

- **触发**：A0 图纸、海报、扫描长图导出的 PDF（页面 4000×5000 pt）。
- **影响**：`size.toSize() * 2.0` 直接渲染成 8000×10000 = 80 M 像素，
  实测 RSS **+306 MB**；再叠一次 OCR 预处理，低内存机器直接 OOM 或长时间卡死。
- **修复**：`clamp_render_size()` 限制单边 ≤ 4096、总像素 ≤ 16 M，超出等比降采样；
  普通 A4 仍按 2 倍（1190×1684）不受影响。
- **验证**：4000×5000 pt → 3276×4096（≈13 M 像素）；A4 → 1190×1684 不变。

#### P2-4　长截图把「纯色/重复内容」误判成到底，提前结束

- **触发**：选区顶部是纯色块（深色背景留白、空白表格区）；或内容高度周期性
  （代码行、重复表格行）。
- **影响**：`matchTemplate` 在纯色模板上会处处得 1.0、`loc` 退化到 (0,0)，
  被判成 `nomotion`，连续 3 帧就结束采集；周期性内容同理会出现等分峰值。
- **修复**：模板标准差 < 1 视为无纹理直接 `append`；命中后**用整帧/重叠区像素复核**
  （平均灰度差 > 阈值则判为误匹配，改走 `append`），并对 `NaN` 打分兜底。
- **验证**：纯色帧 → `append`；整页随机图两帧重叠 → `overlap` 且拼接结果与整页逐字节相同；
  周期条纹 → 不再出现 `nomotion`。

#### P2-5　启动后立刻改设置会整窗冻结约 1.8 秒

- **触发**：程序启动（预热线程正在构造 RapidOCR、持锁 1–3 秒）时打开设置改语言/角度分类。
- **影响**：`OCREngine.reload()` 去抢同一把 `_LOAD_LOCK`，主线程被阻塞到预热结束。
  实测 **1845 ms** 无响应。
- **修复**：`reload()` 改为无锁清引用 + `generation` 版本号；初始化线程发现版本变了就
  不把旧参数引擎写回缓存（否则设置会被静默丢弃）。
- **验证**：reload 耗时 **0 ms**；初始化期间 reload 后 `_engine` 仍为 None（旧引擎未回写）。

#### P2-6　docx 导出是 O(n²)：10 万行 419 秒

- **触发**：导出历史上百万字符、或批量识别几百张图后一次性导出 docx。
- **影响**：`doc.add_paragraph()` 每行内部做一次 O(n) 插入，
  实测 2 000 行 0.28 s、10 000 行 2.3 s、50 000 行 **93.6 s**、100 000 行 **419 s**
  （PDF 同为 146 s）。虽然已在线程里跑，但用户会以为卡死。
- **修复**：改为直接构造 `<w:p><w:r><w:t xml:space="preserve">` 并插到 `w:sectPr` 之前，
  输出结构与 `add_paragraph` 完全一致（空行仍为空段落、行首空格保留）。
- **验证**：100 000 行 **3.4 s**（约 123 倍），回读 100 000 段、内容与特殊字符一致。

#### P2-7　长截图预览里的「识别」绕过忙碌检查

- **触发**：批量识别/PDF 识别进行中，从长截图预览点「识别并复制」。
- **影响**：只检查了 `_worker`，会同时跑两个识别任务（同一 RapidOCR 实例并发推理），
  内存翻倍、结果串扰风险。
- **修复**：改用统一的 `_check_ocr_busy()`（并把长截图线程也纳入检查）。
- **验证**：任一线程在跑时返回提示，不再启动第二个任务。

## 8. 第三轮：把「已知限制」逐个消掉

### 8.1 结论速览

| # | 上一轮的「限制」 | 根因 | 现在的结果 |
| --- | --- | --- | --- |
| 1 | 混合 DPI 多屏，接缝处 1–2 px 误差 | 整个虚拟桌面用**一个**统一缩放比绘制/裁剪 | 逐屏配对，每屏用自己的物理/逻辑比例；单屏时数值与旧算法逐个相等 |
| 2 | 无框线且列间距 < 0.9 倍字高的表格会并成一列 | 切列阈值绑死在「字高」上 | 改成按**全局空白缝**切列：5 px 缝（0.25 倍字高）也能正确切成 3 列 |
| 3 | 页面有视频/滚动条时拼接断裂 | ① 顶部条被噪声污染 → 匹配失败 ② 局部动态区域让像素复核整体否决 | 缩略粗搜 + 候选复评 + 「逐列差异中位数」判定 + 动态列自动屏蔽 |

### 8.2 混合 DPI 多屏：逐屏配对

**问题**：`grab_virtual_screen()` 抓的是整块虚拟桌面（物理像素），但绘制和裁剪都用
`raw.width / geo.width()` 这一个比值。两块屏 DPI 不同时，这个比值是两者的加权平均：
100% 的屏被放大、125% 的屏被压缩，跨屏选区裁出来的图右半边会错位 1–2 px，
文字边缘发虚。

**修复**（`app/ui/capture_overlay.py`）：

- 新增 `screen_boxes()`：把每个屏幕的**逻辑矩形**与其在截图内的**物理矩形**配成一对。
  配对用归一化坐标的最小距离（Qt 与 mss 的屏幕顺序不保证一致，不能按下标配）。
- `_phys_rect()`：逻辑选区先与每块屏求交，用该屏自己的 `phys/logical` 比例换算，
  再求并集；跨屏选区得到的是各屏精确片段的并。
- 绘制同理：`paintEvent` 逐屏 `drawPixmap(该屏逻辑矩形, pixmap, 该屏物理矩形)`。
- 绘制用的副本把 `devicePixelRatio` 归零：否则 Qt 会按统一 dpr 再缩放一次，
  把逐屏的精确比例又抹平回去。
- `_grab_all()` 只开一次 mss，同时拿到图像与显示器列表（不让「抓屏」变成两次）。
- 拿不到显示器信息时（mss 异常、测试里构造）自动退回旧的单比例算法，
  因此 `t_verify.py` 里 5 个坐标断言数值不变。

**实测**（`.workbuddy/t_overlay_draw.py`）：构造「左屏 1:1 + 右屏 2:1」的混合 DPI 布局，
截图左半蓝、右半红。按屏绘制后**分界线落在 x=50**；若仍用统一比例（150→100 均匀拉伸），
分界线会落在 x≈33 —— 这 17 px 就是以前跨屏截图右半边文字发虚、边缘错位的原因。
6 个断言全过（含两块屏各自的物理矩形换算）。

### 8.3 密集表格：按「全局空白缝」切列

**问题**：`_cells_from_row()` 用 `0.9 × 行高中位数` 当列间隙阈值。列间距再窄一点
（密集排版、小字号截图）就整片并成一列，导出 Excel 时整张表只剩一列。

**修复**（`app/core/engine.py`）：新增 `_corridor_bounds()`。

- 列出所有字框的左右边缘作为候选点；相邻两点之间的横坐标区间如果**全表没有任何
  一行有文字跨越**，它就是一道列缝。
- 缝宽只取决于「有没有字压在上面」，**与字高无关**，所以 5 px 的缝也能切对。
- 允许 `25%` 的行压过缝隙：表头跨列标题、合并单元格不会被当成多切一列。
- 跨过列缝的字框（「合计」这类合并标题）落到它占据的**第一列**，而不是按中心点
  塞进中间那列。
- 找不到任何缝（普通文本、某行文字横跨多列被识别成一个框）时退回旧的区间合并算法，
  老行为不倒退。列数上限 16，超过说明 word box 噪声太多。

**实测**（`t_dyn.py` 之外的直接用例）：

| 输入 | 旧算法 | 现在 |
| --- | --- | --- |
| 列间距 5 px、字高 20 | 1 列（全并） | 3 列，每行长度一致 |
| 3×3 带一个空单元格 | 3 列但右侧列左移 | 3 列，空格留 `""` |
| 末尾加一行跨列「合计」 | 多切一列 | 3 列，「合计」落在第 1 列 |
| 真实渲染表格图（OCR 端到端） | 3×3 | 3×3，逐格一致 |

### 8.4 长截图：动态内容不再让拼接断裂

**问题**：页面上有一块固定位置的动态内容（视频、滚动条滑块、走秒的时钟）时，
重叠区像素永远对不上，`_mean_diff > 18` 直接判「拼不上」→ 整帧追加 →
长图里出现一整段重复内容。

**修复**（`app/core/stitcher.py`），三层递进：

1. **缩略粗搜**：模板（新帧顶部 100 px）和搜索区都按 4×4 均值缩到 1/4 后再匹配。
   随机噪点在缩小后被平均掉，排版结构还在，相关系数不再被视频区拖垮；
   锁定大致位置后再用全分辨率在小窗口内 `_refine()` 细化。
2. **候选复评 + 逐列中位数判定**：取相关系数前 4 个峰值，逐个算像素差，新增第三个指标
   ——**逐列差异比例的中位数**。对得齐时绝大多数列几乎完全一致，只有视频那几列对不上，
   中位数为 0；对不齐时整体都差，中位数很高。比「面积占比」更能区分
   「局部动态内容」和「整段错位」。相关系数下限从 0.75 降到 0.35，
   真正裁决交给像素复核（0.75 卡关正是视频场景必然失败的原因）。
3. **动态列屏蔽**：连续两轮都对不上的像素列被记入 `_ignore`，
   之后既不参与匹配（填成常数，对相关系数无贡献）也不参与复核。
   这样即使动态区域很大，第一帧之后也能稳定拼接。

另外，平均差打平时选**重叠更小**的候选：周期性内容每个峰值都像素相同，
挑最小重叠才不会把正常滚动误判成「页面已到底」。

**实测**（`.workbuddy/t_dyn.py`，10 个断言）：

| 场景 | 修复前 | 现在 |
| --- | --- | --- |
| 静态页面滚动 5 帧 | 900 px ✓ | 900 px ✓（逐像素等于整页） |
| 固定位置视频（180×200 噪点，占 22% 面积） | 2400 px（5 次 append） | **900 px（5 次 overlap）** |
| 滚动条滑块移动 | 900 px ✓ | 900 px ✓ |

### 8.5 单实例：内核互斥体仲裁

**问题**：`QLocalServer` 只能「尽力」保证单实例。两个进程几乎同时启动时，
双方都还没 `listen`，`_notify_running_instance()` 都返回 False，于是双双创建主窗口——
两套全局键盘钩子（按一次热键弹两个遮罩）、两份历史快照互相覆盖。

**修复**（`app/main.py`）：

- `_acquire_instance_lock()`：Windows 用 `CreateMutexW("Local\\SnapOCR-single-instance")`，
  `ERROR_ALREADY_EXISTS` 即判定已有实例。互斥体是内核对象，进程一死立刻释放，
  不存在锁文件残留；`CreateMutexW` 的 `restype` 显式设成 `c_void_p`，
  否则 64 位下句柄会被截断。
- 非 Windows 用 `QLockFile`（带进程存活校验）。
- 抢锁失败后重试唤起 12 次（每次 80 ms）；仍连不上就弹一句
  「已经在运行，请从托盘打开」再退出，而不是静默消失。
- `QLocalServer` 的角色降级为「唤起已存在的窗口」，并且**提前到主窗口创建之前** listen，
  把「抢到锁但还没准备好被唤起」的窗口期缩到最小。
- `--multi` 仍旧跳过全部单实例逻辑（排查问题用）。

**实测**（`.workbuddy/t_single.py`，7 个断言全过）：

| 场景 | 结果 |
| --- | --- |
| 先起 A，再起 B | B 在 **0.80 s** 内退出码 0，A 不受影响 |
| 同时启动 3 个 | 存活 **1** 个 |
| 全部退出后再启动 | 正常（锁无残留） |
| `--multi` 两个进程 | 都在（保留调试口子） |

### 8.7 仍然保留的取舍（诚实的边界）

这几项不是「懒得修」，而是修了会引入更大代价，或者依赖不可控的外部条件：

- **PDF 超长文本导出慢**：`QTextDocument` 的分页布局是 Qt 内部实现，
  换第三方库会丢掉现有排版与中文换行效果。已在后台线程 + 可取消。
- **长截图的滚动注入依赖 Win32**：`mouse_event` 在非 Windows 上不可用，
  这是平台能力问题，不是缺陷；启动时会明确提示。
- **动态内容会被「复制」进长图**：固定位置的视频在滚动过程中出现在不同高度，
  物理上无法只保留一份。本轮解决的是「不因此断裂」，不是「消除重复画面」。
- **OCR 本身的分词粒度**：表格列的正确性依赖 word box 的准确性；
  一个字被识别成两个框时仍可能多切一列（已用「允许 25% 行压缝」兜住常见情况）。
