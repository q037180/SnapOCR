# 技术长文 ①：10 万行导出从 419 秒到 3.4 秒

> 发掘金 / 知乎专栏 / 博客园。正文整段复制，配图见文末。
> 口径与 `docs/QA-REPORT-2026-11-06.md` 第 7 章一致，数字都是实测。

## 标题（选一条，别堆）

1. 10 万行导出从 419 秒到 3.4 秒：python-docx 里那个 O(n) 插入
2. 同一个导出按钮，10 万行要跑 7 分钟，我把它改成了 3 秒
3. 一次 O(n²) 排查：不是磁盘慢，不是编码，是 `add_paragraph`

## 正文

压测一个本地 OCR 工具时，我给「导出 docx」喂了 10 万行文本。

结果：**419 秒**。将近 7 分钟。同样的 10 万行，导出 txt 是 **0.01 秒**。所以瓶颈既不在读文本，也不在写磁盘，只可能在 docx 这一条路径上。

### 先排除最容易怀疑的三个

- **不是磁盘**：同一台机器写 20 MB 的 txt 不到 1 秒；
- **不是编码**：UTF-8 编码 10 万行是毫秒级；
- **不是 OCR / 排版**：传进去的已经是拼好的纯文本，循环里只做一件事 —— 逐行 `doc.add_paragraph(line)`。

那就只剩这一行了。

### 增长曲线暴露了问题

按行数分档计时（同一台机器，同一份内容）：

| 行数 | 原实现 |
| --- | --- |
| 2 千 | 0.28 s |
| 1 万 | 2.3 s |
| 5 万 | **93.6 s** |
| 10 万 | **419 s** |

5 万到 10 万只翻了一倍行数，耗时翻了 4.5 倍；1 万到 5 万翻 5 倍，耗时翻了 40 倍。典型的 O(n²) 甚至更陡。`add_paragraph` 看着像「往末尾追加一个段落」，但它要在 XML 树里把新节点插到 `w:sectPr`（节属性，必须是 body 的最后一个元素）之前；每插一个，前面已经堆着的兄弟节点都要被走一遍。再叠上高层 API 每次调用的样式解析、段落对象包装和 XML 往返，10 万次调用就把固定开销放大成了灾难。

一句话：**看起来是 append，实际是反复在长链表尾部做插入。**

### 改法：绕过高层 API，直接拼 OOXML

`w:p` 的结构很简单，一个段落一个 run 一个 text：

```python
from docx import Document
from docx.oxml import OxmlElement
from docx.oxml.ns import qn

doc = Document()
body = doc.element.body
sect = body.find(qn("w:sectPr"))  # 节属性必须是 body 最后一个元素
for line in text.splitlines():
    p = OxmlElement("w:p")
    run = OxmlElement("w:r")
    t = OxmlElement("w:t")
    t.text = line
    t.set(qn("xml:space"), "preserve")  # 保留行首/行尾空格
    run.append(t)
    p.append(run)
    if sect is not None:
        sect.addprevious(p)
    else:
        body.append(p)
doc.save(path)
```

关键是 `sect.addprevious(p)`：直接拿到尾部锚点插入，不再每次从头定位；同时省掉 `add_paragraph` 那一整套对象包装。每行成本变成常数，整体线性。

**结果：10 万行 3.4 秒，约 123 倍。** 回读 docx，10 万个段落、内容与特殊字符逐条一致。

两个容易踩的小点：

- `xml:space="preserve"` 必须加，否则行首缩进会被 Word 吃掉；
- `w:sectPr` 一定要留在 body 最后，插到它后面会导致文档打不开。所以是 `addprevious`，不是 `append`。

### 顺带清掉的三个同源坑

同一轮审查里，还有三个「平时看不出来、量一大就炸」的问题，根子都是**没想过输入规模**：

**① 启动后立刻改设置，整窗冻结 1845 ms。** 引擎预热线程持有 `_LOAD_LOCK` 1–3 秒，而设置变更调用的 `reload()` 也要抢这把锁，主线程就干等着。改成 `reload()` 只无锁清引用，并发安全交给 `_ensure_loaded` 的双检锁，再用 `_generation` 版本号防止旧引擎把结果写回缓存。锁没消失，只是从「主线程等」变成了「后台自己协调」。

**② 超大 PDF 单页吃掉 306 MB。** 4000×5000 pt 的页面按 2 倍缩放渲染就是 8000×10000 的图。加 `clamp_render_size()`：单边不超过 4096、总像素不超过 1600 万，问题页被钳到 3276×4096。OCR 本来也不需要那么高的分辨率，多出来的像素全是纯浪费。

**③ xlsx 里以 `=` 开头的文本被写成公式。** 识别结果里出现 `=SUM(...)` 这类字符串时，openpyxl 会当成真公式，Excel 打开就报错，更糟的是这是条公式注入路径。写完之后补一句 `cell.data_type = "s"`，强制按文本处理。同理，文本里的 NUL 等 XML 非法控制字符会让 docx 直接抛异常，写之前统一过滤。

### 结论

这四件事没有一件需要换库、换架构或者加机器。共同点只是：**平时跑 100 行都对，跑到 10 万行才暴露**。给自己提的一个检查习惯是，遇到「逐条处理」的循环，先按 1 千 / 1 万 / 5 万 / 10 万分档计一次时 —— 曲线是直的还是弯的，比读源码猜快得多。
